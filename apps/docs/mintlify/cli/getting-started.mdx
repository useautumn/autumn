The `atmn` CLI keeps your Autumn catalog — features, plans, versions, rewards — in an `autumn.config.ts` file. `atmn push` makes the server match the file; `atmn pull` writes the server's catalog back into it.

## Installation

Run it straight from your package manager:

<CodeGroup>

```bash bunx
bunx atmn
```

```bash npx
npx atmn
```

```bash pnpm
pnpm dlx atmn
```

</CodeGroup>

`atmn init` adds the package as a dependency and writes an `atmn` script to your root `package.json`, so afterwards you can run `bun atmn push`, `npm run atmn push`, and so on.

## Initialize a project

```bash
bunx atmn init
```

`init` does the whole setup: "connect to Autumn, place the config, pull your catalog, install the skills".

1. **Connect.** With no usable `AUTUMN_SECRET_KEY` on disk, it asks how you want to connect:
   - `--login` — "sign in on the web (opens a browser; prints the URL if it can't)". Writes `AUTUMN_SECRET_KEY` (sandbox) and `AUTUMN_PROD_SECRET_KEY` (production) to your `.env`.
   - `--keyless` — "create a sandbox org now, no account needed; link it to an account later with `atmn login --claim <email>`". Writes only `AUTUMN_SECRET_KEY`.

   Without a TTY (or with `--headless`) it prints the two flags and stops instead of prompting, so re-running with the flag continues from there.
2. **Place the config.** Scaffolds `autumn.config.ts`, `features.ts`, `plans.ts` and `rewards.ts`, adds `atmn` to `package.json`, and installs dependencies. In a monorepo it asks where the package should live (`--path <dir>`) and what to call it (`--name <name>`).
3. **Pull your catalog.** Whatever the org already has is written into the collection files.
4. **Install the skills.** The bundled agent skills are written to `<config folder>/skills`, so your coding agent can read them. `npx skills add <dir> -y` makes them visible to the agent.

```bash .env
AUTUMN_SECRET_KEY=am_sk_test_...
AUTUMN_PROD_SECRET_KEY=am_sk_live_...
```

<Check>
`bunx atmn env` prints the org, environment and key your commands would target, plus notes on anything that looks wrong. `--json` gives an agent-readable version.
</Check>

## Edit the config

`autumn.config.ts` imports each collection and passes them to `atmn()`:

```ts autumn.config.ts
import { atmn } from "atmn";
import { features } from "./features";
import { plans } from "./plans";
import { rewards, referralPrograms } from "./rewards";

export default atmn({
	features,
	plans,
	rewards,
	referralPrograms,
	settings: {},
});
```

The collection files hold the fixtures:

```ts plans.ts
import { plan } from "atmn";

export const plans = [
	plan({
		planId: "pro",
		versionSlug: "v2",
		active: true,
		name: "Pro",
		price: { amount: 20, interval: "month" },
		items: [
			{
				featureId: "messages",
				included: 10000,
				reset: { interval: "month" },
			},
		],
	}),
];
```

Each collection you state is the complete desired state for it: a plan, version or variant you leave out is a deletion (archived when customers hold it). A collection you leave out of `atmn({...})` entirely is not managed. See the [configuration reference](/cli/config) for every field.

## Push

`atmn push` is the preview. It never prompts and never writes:

```bash
bunx atmn push
```

It lints the config, sends it to the server as a preview, and prints the diff: created, updated, deleted and archived rows, the customers affected, and any migration drafts the change would create.

Apply exactly what the preview showed with `--yes`:

```bash
bunx atmn push --yes
```

`push --yes` also writes each row's server-side `internalId` (and any `versionSlug` the server assigned) back into your fixtures. Those edits are expected — a row carrying an `internalId` can be renamed instead of deleted and recreated.

Use `-d`/`--dry-run` to force preview-only behaviour even when `--yes` is passed.

<Warning>
Commands target your sandbox by default. Add `-p` to target production: `bunx atmn push -p --yes`.
</Warning>

## Pull

```bash
bunx atmn pull
```

`pull` writes the server's catalog back into the config in place: it appends rows the config never mentioned, flips `active` where someone promoted a version in the dashboard, and backfills `internalId` and `versionSlug`. Run it after anyone edits the dashboard, and before editing a config you did not write.

`atmn pull --overwrite --yes` is the escape hatch: it deletes every TypeScript file in the config folder and rescaffolds from the server. Reach for it only when the config describes a different org than your key.

## Sandboxes

`atmn sandbox create <name>` mints an isolated sandbox and saves its key; `atmn sandbox use <name|id>` pins `AUTUMN_SANDBOX_ID` so every later command targets it, until `atmn sandbox use --clear`.

`atmn reset --yes` wipes the targeted sandbox's catalog and customers (keys and settings stay), and `atmn push --yes` rebuilds it from your config.
