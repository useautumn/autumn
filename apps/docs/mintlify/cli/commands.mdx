The CLI's own help is the source of truth: `atmn --help`, or `atmn <command> --help`.

## Global flags

These are accepted by every command.

| Flag | Description |
|------|-------------|
| `-p, --prod` | target production instead of sandbox |
| `--sandbox <sandboxId>` | target a specific sandbox |
| `-l, --local` | target a local server (default port 8080) |
| `--port <port>` | port of a local server (implies `--local`) |
| `-b, --base-url <url>` | send to this URL instead |
| `--client-id <id>` | OAuth client id the CLI identifies as |
| `-c, --config <path>` | `autumn.config.ts`, or the folder holding it (default: found from cwd or the root `package.json`) |
| `--headless` | never prompt: print what a command needs and stop (default when not a TTY) |
| `-V, --version` | print the version |

`-p` and `--sandbox` cannot be combined — `--prod` overrides a pinned sandbox rather than addressing it. The most specific destination wins: `--base-url`, then `--local`/`--port`, then `AUTUMN_BASE_URL`, then Autumn's API.

## `atmn init`

"set up this repo: connect to Autumn, place the config, pull your catalog, install the skills"

```bash
atmn init [options]
```

| Flag | Description |
|------|-------------|
| `--path <dir>` | folder for the Autumn package (monorepos) |
| `--name <name>` | the package's name (monorepos) |
| `--login` | sign in on the web (opens a browser; prints the URL if it can't) |
| `--keyless` | create a sandbox org now, no account needed; link it to an account later with `atmn login --claim <email>` |

With no `AUTUMN_SECRET_KEY` on disk, `init` asks how to connect in a terminal; headless it prints `--login` / `--keyless` and stops. Pick one of the two — passing both is an error.

It scaffolds `autumn.config.ts`, `features.ts`, `plans.ts` and `rewards.ts`, adds the `atmn` dependency and an `atmn` script to `package.json`, runs your package manager's install, pulls the org's catalog into the config, and writes the bundled skills to `<config folder>/skills`.

## `atmn login`

"connect to Autumn and write the org's keys to your .env"

```bash
atmn login [options]
```

| Flag | Description |
|------|-------------|
| `--keyless` | create a sandbox org now, no account needed; link it to an account later with `atmn login --claim <email>` |
| `--claim <email>` | link the keyless org this key belongs to with an account |

A plain `atmn login` authorizes in a browser (printing the URL when it cannot open one) and writes `AUTUMN_SECRET_KEY` and `AUTUMN_PROD_SECRET_KEY` to your `.env`. `--keyless` provisions a sandbox org with no account and writes `AUTUMN_SECRET_KEY` only. `--claim <email>` creates and emails a browser claim link that attaches a keyless org to an account; the existing key stays valid. `--keyless` and `--claim` cannot be combined.

## `atmn env`

"show the org, environment and key your commands target"

```bash
atmn env [--json]
```

| Flag | Description |
|------|-------------|
| `--json` | print the response instead of the summary |

`--json` reports the organization, environment, whether the key is the main sandbox key, the claim state, the pinned sandbox, the key name and base URL, plus `notes` naming the fix for anything that looks wrong.

## `atmn push`

"preview `autumn.config.ts` against your catalog; `--yes` applies it"

```bash
atmn push [options]
```

| Flag | Description |
|------|-------------|
| `-y, --yes` | apply the changes the preview shows |
| `-d, --dry-run` | preview only, even with `--yes` |

`push` never prompts: a plain `push` lints the config, previews the diff and applies nothing, and `--yes` is the only gate — deletions included. Settings are previewed and applied first, on their own, because a flag like `multiCurrency` changes what the catalog accepts.

After a successful `push --yes` the CLI writes each row's `internalId` — and any `versionSlug` the server assigned — back into your fixtures, and lists the migration drafts the update created.

## `atmn pull`

"write your remote catalog back into `autumn.config.ts`"

```bash
atmn pull [options]
```

| Flag | Description |
|------|-------------|
| `--include-mappings` | keep processor mappings in pulled fixtures |
| `--overwrite` | discard the local config and pull the catalog fresh (e.g. after switching orgs) |
| `-y, --yes` | overwrite it |

A plain `pull` edits in place: it appends rows the config never mentioned, updates changed ones, flips `active`, and backfills `internalId` and `versionSlug`. It can only edit fixtures that are plain literals — a spread, helper call or `.map()` makes a row unlocatable, and the pull reports which rows and writes nothing.

`--overwrite` deletes every TypeScript file under the config folder and rescaffolds from the server, so it requires `--yes`; without it, `pull` prints what would happen and stops.

## `atmn reset`

"wipe this sandbox's catalog and customers; `--yes` applies it"

```bash
atmn reset [-y]
```

| Flag | Description |
|------|-------------|
| `-y, --yes` | wipe it |

Wipes every customer, plan, feature and migration draft in the targeted sandbox — the pinned one when `AUTUMN_SANDBOX_ID` is set, otherwise your main sandbox. Keys and settings stay. Without `--yes` it names the sandbox and stops.

<Warning>
`reset` refuses a live key before it sends anything: "Reset only wipes sandboxes; the key for this target is a live key."
</Warning>

## `atmn skills`

"the skills this CLI carries: list, print, install, update"

```bash
atmn skills [name] [options]
```

| Argument / flag | Description |
|------|-------------|
| `[name]` | print this skill's `SKILL.md` |
| `--ref <path>` | print one of the skill's references instead |
| `--json` | print the skill as JSON |

With no name it lists the bundled skills. The CLI carries `autumn-setup`, `autumn-catalog`, `autumn-integrate` and `autumn-concepts`; `push` and `pull` print a hint when the copy next to your config is older than the CLI's.

### `atmn skills install`

"write the skills next to your config; `--link` runs `npx skills add`"

| Flag | Description |
|------|-------------|
| `--dir <dir>` | write here instead of `<config folder>/skills` |
| `--link` | run `npx skills add <dir> --all` afterwards |

### `atmn skills update`

"rewrite installed skills older than this CLI's"

| Flag | Description |
|------|-------------|
| `--dir <dir>` | the install to update; `<config folder>/skills` by default |

## `atmn sandbox`

"manage isolated sandboxes"

Sandbox management is an organization operation, so `list`, `use`, `create` and `delete` authenticate with the main `AUTUMN_SECRET_KEY` even when a sandbox is pinned.

### `atmn sandbox list`

"show your sandboxes, newest first"

| Flag | Description |
|------|-------------|
| `--json` | print the response instead of the table |

### `atmn sandbox use`

"target a sandbox by name or id; `--clear` returns to the main one"

```bash
atmn sandbox use [query] [options]
```

| Argument / flag | Description |
|------|-------------|
| `[query]` | the sandbox's name or id |
| `--clear` | drop the pin so commands target the main sandbox |
| `--json` | print the result as JSON |

Pins `AUTUMN_SANDBOX_ID` in your `.env`; every command targets that sandbox until you clear it. If this machine has no key for the sandbox, `use` mints one and writes it as `AUTUMN_SANDBOX_<ID>_SECRET_KEY`. With no query in a terminal it asks which sandbox.

### `atmn sandbox create`

"mint a sandbox and write its key to your .env"

```bash
atmn sandbox create <name> [options]
```

| Argument / flag | Description |
|------|-------------|
| `<name>` | name for the sandbox |
| `--color <color>` | colour the dashboard labels it with |
| `--icon <icon>` | icon the dashboard labels it with |
| `--use` | pin `AUTUMN_SANDBOX_ID` so later commands target it |
| `--json` | print the response instead of the summary |

The key is readable exactly once, in the create response. If the `.env` write fails, the CLI prints the key so you can save it yourself.

### `atmn sandbox delete`

"delete a sandbox and drop its key from your .env"

```bash
atmn sandbox delete <id> [-y]
```

| Argument / flag | Description |
|------|-------------|
| `<id>` | id of the sandbox to delete |
| `-y, --yes` | delete it, catalog and customers included |

Without `--yes` it names the sandbox and stops. After deleting, it removes that sandbox's key from every `.env` holding it, and the pin where it pointed at that sandbox.

## Environment variables

Read from `.env.local` then `.env`, searched from the config folder, the repo root and the current directory. Anything already in `process.env` wins.

| Variable | Used for |
|----------|----------|
| `AUTUMN_SECRET_KEY` | the sandbox key; the default for every command, and always the key for `sandbox` subcommands |
| `AUTUMN_PROD_SECRET_KEY` | the production key, used when `-p` is passed |
| `AUTUMN_SANDBOX_<ID>_SECRET_KEY` | a named sandbox's own key, used when that sandbox is pinned or passed to `--sandbox` |
| `AUTUMN_SANDBOX_ID` | the pinned sandbox, written by `atmn sandbox use` and `atmn sandbox create --use` |
| `AUTUMN_BASE_URL` | send to this URL instead of Autumn's API |
| `AUTUMN_CLIENT_ID` | the OAuth client id the CLI identifies as |

A missing key fails before anything is sent, and names the fix:

```
AUTUMN_SECRET_KEY is not set. Run atmn login, or atmn login --keyless if you don't have an account.
AUTUMN_PROD_SECRET_KEY is not set. Run atmn login.
AUTUMN_SANDBOX_<ID>_SECRET_KEY is not set. Run atmn sandbox create, or add its key to your .env.
```

## Headless mode

`--headless` — or any non-TTY run, such as CI or an agent — turns every prompt into a printed instruction: the command says which flag it needed and stops without failing. Re-run with that flag to continue. `push` and `pull` never prompt in the first place; `--yes` is their only gate.
